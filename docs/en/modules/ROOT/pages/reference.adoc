== Major public API (`io.vidocq.chappe.api`)

=== `Server`

[source,java]
----
public interface Server extends AutoCloseable {
    void start();
    void stop();
    int port();
    static Builder builder();

    interface Builder { ... }
}
----

The builder is the nested `Server.Builder` interface:

* `port(int)`
* `host(String)`
* `handler(Handler)`
* `backlog(int)`
* `readTimeout(Duration)` / `writeTimeout(Duration)` / `idleTimeout(Duration)`
* `maxRequestSize(long)` / `maxDrainSize(long)` [.tag-new]#NEW#
* `maxHeaderSize(int)` — the request header section, 8 KiB by default. HTTP/1.1 counts its raw bytes and answers `431` past it. Over HTTP/2 it also sets the limits on a header list [.tag-new]#NEW#:
** the advertised `SETTINGS_MAX_HEADER_LIST_SIZE`, S below, is `maxHeaderSize + 32 * 100` (11,392 bytes by default), measured as RFC 9113 §6.5.2 does (each name and value plus 32 per field), so a section HTTP/1.1 accepts fits;
** a list past it is still decoded, so the HPACK context of the connection stays intact, and its stream alone gets `431 Request Header Fields Too Large`, then `RST_STREAM(NO_ERROR)` if its body has not ended; the handler is not called. A gRPC call gets the same HTTP `431` before it is routed, which gRPC clients report as `UNKNOWN` (the gRPC mapping of HTTP statuses). Trailers past it reset their stream with `RST_STREAM(ENHANCE_YOUR_CALM)`;
** the hard caps answer abuse with `GOAWAY(ENHANCE_YOUR_CALM)`, which ends the connection: a header block (HEADERS plus CONTINUATION) of more than `max(4 * S, 64 KiB)` encoded bytes (65,536 by default), or a list of more than `max(8 * S, 256 KiB)` decoded bytes (262,144 by default, an HPACK amplification);
** the setting is advisory: RFC-compliant clients do not send a larger list, so the `431` serves the clients that ignore it.
* `tls(SSLContext)` — TLS, no client certificate (`ClientAuth.NONE`)
* `tls(SSLContext, ClientAuth)` [.tag-new]#NEW# — TLS with a client certificate mode, see xref:usage.adoc#client-certificates[Usage — client certificates]; the last `tls(...)` call wins for both context and mode
* `alpnProtocols(String...)`
* `shutdownGracePeriod(Duration)`
* `build()` returns a `Server`

The executor is not configurable: every connection is handled on its own virtual thread.

[#timeouts]
==== Timeouts

* `readTimeout` (default 30 s) [.tag-new]#NEW# bounds *each* blocking read of a request body. Over HTTP/1.1 (plaintext and TLS) it bounds each socket read, including the drain of a body the handler left unread; when no byte arrives for that long, the read throws `java.net.SocketTimeoutException` and Chappe closes the connection. Over HTTP/2 it bounds the wait for the stream's next DATA frame; when it expires, the read throws `java.net.SocketTimeoutException`, and, if the request body has not ended, the stream is reset once the response is sent. A call the router sends to a gRPC handler (`Router.grpc`), or to a gRPC-Web handler (`Router.grpcWeb`) in binary mode (`application/grpc-web`), is exempt: a client or bidi streaming call may pause for as long as it likes, and is held until the client or the connection ends it. A gRPC-Web call in text mode (`application/grpc-web-text`) is not: Chappe reads its whole base64 body before decoding it, and a stalled body resets the stream with `RST_STREAM(INTERNAL_ERROR)`. The exemption follows the route, not the request: a gRPC `content-type` on a request to any other handler leaves it bounded. It bounds each read, not the whole body: an upload is not cut as long as each read makes progress within the timeout. Over plaintext one byte is progress; over TLS a read returns only once a whole TLS record (up to 16 KiB) has arrived, so a client must deliver each record within `readTimeout`. `Duration.ZERO` or a negative value disables it; a value too large to count in nanoseconds (such as `ChronoUnit.FOREVER.getDuration()`) is saturated to about 73 years. Until 0.3.0 the value was accepted by the builder and never applied.
* `idleTimeout` (default 60 s) bounds inactivity on the read side: a connection that sends nothing for that long is closed. [.tag-new]#NEW# It also bounds the whole TLS handshake, as a total deadline rather than a bound on each read: a client that has not completed its handshake `idleTimeout` after the server started it is disconnected, even if it keeps sending bytes (CHAPPE-028). The first read after the handshake and the HTTP/2 connection preface are not covered yet. Use a positive value: zero or a negative value removes the handshake deadline, but it does not disable the idle bound, and a connection waiting for a request may then be closed at once. A very large value, up to `ChronoUnit.FOREVER.getDuration()`, is accepted and saturated.
* `writeTimeout` (default 30 s) [.tag-new]#NEW# bounds *one* blocking write of a response, over HTTP/1.1 and HTTP/2: how long the socket may refuse the bytes Chappe is sending, because the client does not read. When it expires, Chappe closes the connection, and the client gets a truncated body. It is not an inactivity bound on the response: nothing is timed while there is nothing to send, so a Server-Sent Events stream with long gaps between events is never cut by it. On HTTP/2 it bounds each write of a flushed frame buffer (up to 16 KiB): when it expires, Chappe closes the whole multiplexed connection, and every stream on it ends with it. Over TLS, a flush is one TLS write of the whole buffer, so the bound covers the whole flush, and the connection is closed at most 100 ms after it. Zero or negative means no bound for responses; the writes of a TLS close (the `close_notify`, and the alert of a rejected handshake) stay bounded, by `writeTimeout` when it is positive and by 2 s otherwise. Until 0.3.0 the value was accepted by the builder and never applied.

[#request-body-limits]
==== Request body limits [.tag-new]#NEW#

* `maxRequestSize` (default 10 MiB) caps a request body. Over HTTP/1.1, a `Content-Length` above it is answered `413 Content Too Large` (RFC 9110 §15.5.14) before the handler runs, and the connection is closed. A chunked body is counted as it is on the wire, framing included (chunk-size lines with their extensions, CRLFs and the trailer section), so a body near the cap with heavy chunk overhead trips slightly earlier than its data alone would. The chunk that would take it past the cap fails the read with `RequestBodyTooLargeException`, an `IOException` whose `limit()` is the cap, before any of that chunk's data is read; every later read of the body throws the same exception. Whatever the cap, one chunk-size line or one trailer line longer than 8 KiB fails the read with an `IOException`. The handler can still answer (a `413` is the usual choice); Chappe then closes the connection gracefully and reads no other request from it. A `RequestBodyTooLargeException` that escapes the handler, as is or as the cause of another exception, is answered `413` instead of `500`, as over HTTP/2.
* `maxDrainSize` (default 1 MiB) bounds what Chappe reads of a body the handler left unread. Over HTTP/1.1, the rest of the body sits between the response and the next request, so Chappe reads and discards it to keep the connection. When more than `maxDrainSize` bytes are left, it closes the connection gracefully instead, after the response; a `WebSocketUpgrade` or `ConnectionUpgrade` answer is refused the same way, and the connection closes without the `101`. A chunked body is counted as it is on the wire, framing and trailers included, and the unread rest of a chunk the handler started counts too. `0` closes the connection whenever a body was left unread. A negative value is refused with `IllegalArgumentException`.
* Over HTTP/2, when the response is complete before the request body ended, Chappe resets the stream with `RST_STREAM(NO_ERROR)` (RFC 9113 §8.1), so the client stops uploading. The DATA, HEADERS and CONTINUATION frames the client had already sent on that stream, or on a stream Chappe refused or reset, are dropped without failing the connection; they still count against the connection window, and their header blocks are still decoded to keep the HPACK table in sync. DATA on a stream that closed normally, or whose request had already ended, is answered with `RST_STREAM(STREAM_CLOSED)`; DATA on a stream that was never opened is still a connection error.
* Over HTTP/2, the stream flow-control window reopens as the handler reads the body, not as DATA arrives: a stream buffers at most its window (64 KiB) of unread body, and a client that sends past the window gets `RST_STREAM(FLOW_CONTROL_ERROR)` for that stream. The connection window is still credited on receipt, so a stream that is not read never blocks the others; a client that sends past the connection window gets `GOAWAY(FLOW_CONTROL_ERROR)`. DATA padding counts against the window and is credited back at once.
* Over HTTP/2, `maxRequestSize` caps the DATA of each stream: the payload counts, the padding does not (flow control bounds it). While the response has not started, the body read fails with `RequestBodyTooLargeException` (the frame that passed the cap is never handed out), Chappe answers `413` instead of the handler's response and, if the client is still sending, resets the rest of the upload with `RST_STREAM(NO_ERROR)`; a handler that does not read the body gets its response replaced by the `413` all the same. Once the response is on its way, the stream is reset with `RST_STREAM(CANCEL)`. A call the router sends to a gRPC handler (`Router.grpc`), or to a gRPC-Web handler (`Router.grpcWeb`) in binary mode, is not capped: it carries a sequence of messages, not one body. Nothing bounds the total such a call receives; each message is bounded only as it is read by the handler, at the receive message size of the gRPC layer (4 MiB). A gRPC-Web call in text mode is capped like a plain body, since Chappe reads it whole before decoding it: a body over the cap ends the call with `grpc-status` `RESOURCE_EXHAUSTED` before the handler runs. Raise `maxRequestSize` for large text-mode uploads. The exemption follows the route, never the request's `content-type`: a plain handler receiving `application/grpc` is capped like any other. Flow control still bounds what a gRPC stream buffers.
* The two protocols differ in one respect. Over HTTP/2, once the body has gone past the cap before the response started, the `413` replaces whatever the handler answers, even a response it built after catching the exception. Over HTTP/1.1, a handler that catches the exception keeps its own response; only an exception that escapes the handler becomes the `413`. On both protocols, a cap failure after the response has started cannot change it: HTTP/1.1 closes the connection, HTTP/2 resets the stream with `RST_STREAM(CANCEL)`.

=== `Router`

[source,java]
----
Router.builder()
    .get(path, handler)
    .post(path, handler)
    .put(path, handler)
    .delete(path, handler)
    .patch(path, handler)
    .head(path, handler)            // also auto for GET
    .options(path, handler)
    .route(method, path, handler)   // explicit HttpMethod
    .group(prefix, sub -> sub.filter(...).get(...))
    .mount(prefix, handler)
    .mount(prefix, handler, stripPrefix)   // control prefix stripping
    .webSocket(path, webSocketHandler)     // RFC 6455 endpoint
    .grpc(path, grpcHandler)               // gRPC over HTTP/2
    .grpcWeb(path, grpcHandler)            // gRPC-Web (browser clients)
    .filter(filter)
    .notFound(handler)
    .build();
----

Behavior:

* automatic `405 Method Not Allowed` with the `Allow` header when the path matches but not the method.
* trailing slash transparent: `/users` and `/users/` map to the same route.
* percent-decoding on path params: `/users/John%20Doe` → `pathParam("id") = "John Doe"`.

=== `ClientAuth` [.tag-new]#NEW#

[source,java]
----
public enum ClientAuth { NONE, WANT, NEED }
----

The client certificate mode of a TLS listener, set with `Server.Builder.tls(SSLContext, ClientAuth)` and read back as `ServerConfig.clientAuth()` (default `NONE`). See xref:usage.adoc#client-certificates[Usage — client certificates].

[cols="1,2,2,2"]
|===
| Mode | No certificate | Trusted certificate | Untrusted certificate

| `NONE` | accepted | not requested | not requested
| `WANT` | accepted, empty `peerCertificates()` | accepted, chain in `peerCertificates()` | handshake fails (JSSE), TLS alert sent
| `NEED` | handshake fails, TLS alert sent | accepted, chain in `peerCertificates()` | handshake fails, TLS alert sent
|===

The mode is applied at the handshake only. A TLS 1.2 client-initiated renegotiation is refused and the connection closed with a `close_notify`, but no alert saying why (no `no_renegotiation`); TLS 1.3 KeyUpdate is still supported. `Request.tls()` therefore describes the session for the whole connection.

[#connection-metadata]
=== Connection metadata on `Request`

[cols="2,3"]
|===
| Method | Value

| `remoteAddress()` / `localAddress()`
| The client and server socket addresses, over cleartext and TLS, HTTP/1.1 and HTTP/2.

| `isSecure()`
| `true` on a TLS connection.

| `scheme()`
| `"https"` on a TLS connection, `"http"` otherwise.

| `tls()` [.tag-new]#NEW#
| `Optional<TlsInfo>`: the TLS session, present exactly when `isSecure()` is `true`, empty on cleartext. All HTTP/2 streams of a connection share it.

| `connectionId()` [.tag-new]#NEW#
| `OptionalLong`: an identifier of the connection, unique within the running server and stable for its lifetime. Every HTTP/1.1 keep-alive request and every HTTP/2 stream of one connection reports the same value.

| `streamId()` [.tag-new]#NEW#
| `OptionalInt`: the HTTP/2 stream identifier (odd and positive), empty over HTTP/1.1.
|===

[source,java]
----
public record TlsInfo(String protocol, String cipherSuite, byte[] sessionId,
                      List<X509Certificate> peerCertificates) { }
----

`TlsInfo` is immutable: the constructor copies `sessionId` and `peerCertificates`, `sessionId()` returns a copy, and `equals`/`hashCode` compare the session id by content. `peerCertificates()` is empty under `NONE`. Wrappers built on `ForwardingRequest` forward `tls()`, `connectionId()` and `streamId()`.

=== YAML schema

[source,yaml]
----
server:
  port: 8080
  bind: 0.0.0.0

static:
  root: /var/www/site
  fallback: /404.html               # status 404
  spa-fallback: /index.html         # status 200 (mutually exclusive with fallback)
  index-files: [index.html]
  cache-control: "max-age=3600, public"
  gzip: true                         # negotiated through Accept-Encoding

headers:
  always:                            # injected on every response
    X-Content-Type-Options: "nosniff"
    Referrer-Policy: "strict-origin-when-cross-origin"
  staging:                           # active when env var STAGING=true
    X-Robots-Tag: "noindex, nofollow"

logging:
  level: INFO
  access-log: false
----

Documented subset: nested maps, inline lists `[a, b]` and block `- item`, string/int/bool scalars, `#` comments. No anchors, no `!!` tags, no multilines.

[#_observability]
== Observability

=== Build identification headers

Every HTTP response from Chappe carries two headers identifying the exact binary that produced it:

[source]
----
Server: Chappe/0.2.0+8d670fb0 (2026-05-09T19:43:04Z)
X-Chappe-Build: Chappe/0.2.0+8d670fb0 (2026-05-09T19:43:04Z)
----

Format: `Chappe/<Maven version>+<short Git hash>(<build timestamp ISO-8601 UTC>)`. Read once at startup via `BuildInfo` (see public API).

* `Server` is the standard header. It can be rewritten by an upstream reverse proxy (NPM, openresty, Cloudflare).
* `X-Chappe-Build` mirrors the same value in a non-standard header that proxies usually forward untouched — useful to identify the binary behind a proxy that sets its own `Server`.

Idempotency: if the application has already set either header on the `Response`, Chappe will not overwrite it.

=== Access log

Enabled via `--access-log` (CLI), `CHAPPE_ACCESS_LOG=true` (env), or `logging.access-log: true` (YAML). CLI overrides env, env overrides YAML.

Format: extended Apache Combined Log Format on `System.out` (captured by Docker/Portainer):

[source]
----
1.2.3.4 - yann.blazart@gmail.com [09/May/2026:18:50:54 +0000] "GET /a.png HTTP/1.1" 200 877719 12ms
----

Field resolution:

* Client IP: `X-Forwarded-For` (first hop) → `X-Real-IP` → `Request.remoteAddress()` → `-`.
* User: `X-Forwarded-User` → `Gap-Auth` (oauth2-proxy) → `-`.
* Size: `Response.body().contentLength()` (or `-` for streamed/chunked bodies).
* Duration: nanoseconds measured by the outermost filter wrapper, captures the final status even if the handler throws.

Available as a public API filter via `Filter.accessLog()` / `Filter.accessLog(Consumer<String>)`; the CLI launcher applies it as the outermost wrapper.

== Maven plugin: pre-compression

[source,xml]
----
<plugin>
  <groupId>io.vidocq.chappe</groupId>
  <artifactId>chappe-static-index-maven-plugin</artifactId>
  <executions>
    <execution>
      <goals><goal>index</goal></goals>
      <configuration>
        <compress>gzip</compress>            <!-- default: none -->
        <compressThreshold>1024</compressThreshold>
      </configuration>
    </execution>
  </executions>
</plugin>
----

Generates:

* `META-INF/chappe-static-index.properties` — O(1) index (path → size + ETag).
* `.gz` sidecars for files above the threshold.

Served zero-copy by `StaticFileHandler.preferPrecompressed(true)`.

== HTTP capabilities

[cols="2,1,3"]
|===
| Spec | Status | Notes

| RFC 9110 (HTTP Semantics) | OK | Date, HEAD/204/304, 405+Allow, Host, 100-continue
| RFC 9112 (HTTP/1.1)       | OK | request parsing, chunked (request and response trailers, §7.1.2), keep-alive, pipelining, lingering close (§9.6, plaintext and TLS) [.tag-new]#NEW#
| RFC 9113 (HTTP/2)         | OK | framing, flow control, lifecycle, GOAWAY, SETTINGS, CONTINUATION, `RST_STREAM(NO_ERROR)` after an early response (§8.1), frames on reset streams ignored (§5.1), stream window reopened as the body is read (§6.9), `SETTINGS_MAX_HEADER_LIST_SIZE` derived from `maxHeaderSize`, a header list past it answered `431` on its stream, a header block (HEADERS plus CONTINUATION) past 64 KiB or a decoded list past 256 KiB by default ending the connection with `GOAWAY(ENHANCE_YOUR_CALM)` (§10.5, §10.5.1) [.tag-new]#NEW#
| RFC 7541 (HPACK)          | OK | static table, dynamic table, Huffman encode/decode; the decoder's table bounded by the advertised `SETTINGS_HEADER_TABLE_SIZE` and the encoder's by the peer's (§4.2), a size update past it or after the first field and a length or integer the block cannot hold answered `GOAWAY(COMPRESSION_ERROR)` (§5.1, §5.2, §6.3) [.tag-new]#NEW#
| RFC 6455 (WebSocket)      | OK | handshake, TEXT/BINARY framing, fragmentation, UTF-8 validation, client masking, close handshake, auto-PONG — over HTTP/1.1
| gRPC over HTTP/2          | OK | transport framing (5-byte prefix), trailers, unary / server-stream / client-stream / bidi, gRPC-Web via `grpcWeb()`
| RFC 9114 (HTTP/3)         | planned | QUIC via the JDK, targeting JDK 26+ — see link:{repo-chappe}/blob/main/ROADMAP.md[ROADMAP.md]
| RFC 8441 (WebSocket H2)   | planned | WebSocket runs over HTTP/1.1 today
|===
